# Suno Create Assistant development notes

## Stack and commands

This is a Manifest V3 Chrome extension built with WXT, React, TypeScript, and pnpm.

Permissions are `['storage']` only. There is no `tabs` permission, no background service worker, and no options page: all styling, presets, mastering management, and keyboard shortcuts run purely in the content script inside the Suno tab itself.

Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e`, and `pnpm build` before handoff. The unpacked build output is `install/suno-create-assistant` (configured via `outDirTemplate` in `wxt.config.ts`, rather than WXT's default `{browser}-mv{manifestVersion}` naming).

For a release zip (e.g. to attach to a GitHub release), run `pnpm zip` only — it runs its own build internally (`wxt zip` rebuilds before zipping), so a separate `pnpm build` beforehand is redundant. It outputs a fixed `install/suno-create-assistant.zip` (`zip.artifactTemplate` in `wxt.config.ts`, overriding WXT's default versioned/browser-suffixed name) so the filename matches the `releases/latest/download/suno-create-assistant.zip` link used in README.md/README_ja.md regardless of version bumps.

## Suno integration rules

- **The content script is injected on every `https://suno.com/*` page and only *runs* on `/create`.** Suno is an SPA, so a client-side navigation (e.g. home -> 作成) never reloads the document; a `/create*`-only `matches` never injected the script in that case and the extension silently did nothing unless `/create` was the entry page. `entrypoints/suno.content.tsx`'s `main(ctx)` therefore decides per URL: `startAssistant()` builds everything (controller, mounts, observers, Cmd/Ctrl+Enter) and returns a teardown; `ctx.addEventListener(window, 'wxt:locationchange', ...)` (WXT's Navigation API watcher) starts it when `isCreatePath()` (`src/suno/route.ts`) becomes true and tears it down when the user leaves. `isDisposed` guards the debounce timer, the clip-button chain and the `initialize()` promise so a queued cycle cannot re-mount the UI after leaving. **`isPageNavigation()` must stay in `sync()`**: the Navigation API also reports downloads, and the backup export's `blob:` link used to look like "left /create" and tore the extension down mid-use (caught by the E2E). `host_permissions` is `https://suno.com/*` to match. The settings dialog host is mounted unconditionally (while running); the styles/presets/title controls only mount while the Advanced tab is active.
- **Extension reloads invalidate the old content-script context before all queued UI work has necessarily stopped.** Every Chrome API access must therefore tolerate `Extension context invalidated`: `src/storage/repository.ts` returns defaults for stale reads, no-ops stale writes/listener registration, and preserves unexpected errors; `SettingsDialog` catches stale `chrome.runtime` metadata reads. WXT's `ctx.onInvalidated` still performs normal teardown. This avoids a late storage/runtime call surfacing as an uncaught page error, but a Suno tab must be reloaded after an extension update to inject the new version.
- **`WorkspaceSwitcher` is temporarily disabled but intentionally retained.** `entrypoints/suno.content.tsx` keeps `WORKSPACE_SWITCHER_ENABLED = false`, so no host is mounted and `SunoAdapter.workspaceListTrigger()` is never called. The current native `ワークスペース` / `Workspaces` breadcrumb navigates to the workspace index instead of opening the visible chooser the feature needs; `docs/alldom_ja.txt` confirms the base DOM has no `ワークスペースを検索` / `Search workspaces` input. Do not re-enable it until a stable in-page chooser is confirmed. When that returns, the retained implementation reads the first ten visible `[role="button"][tabindex]` rows after the localized search input, restores the panel's prior closed state, and selects through the native row only; it must never derive IDs from page-framework state or call an API. It mounts immediately before the native breadcrumb as a normal, non-shrinking flex item. `tests/e2e/extension.spec.ts` pins the disabled state.
- **`MusicalSettingsControls` reads only the current visible Style textarea and never analyses audio.** `detectMusicalSettings()` in `src/domain/logic.ts` recognizes explicit English/Japanese key, BPM, and meter phrases (including Suno's uploaded-audio description style), normalizes key names, and deliberately leaves a field unset when distinct candidates conflict. `SunoController.syncSelectionFromStyleText()` refreshes the detected fields automatically from the deferred Style-input handler and the reconcile pass, so there is deliberately no manual read button. **Dropdown changes rewrite the phrase the Style already states, in place.** Detection is built on positioned spans (`detectMusicalSpans()`: `{ field, start, end, text, value, managed }`, offsets of the *value only*, obtained with the `d`/hasIndices flag on the five regexes). `KEY_NAME`/`BARE_KEY_NAME` and `TEMPO`/`BARE_TEMPO` match the very same characters for "key of D Minor", so spans are de-duplicated by `field:start:end` - without that a replacement is applied twice. `applyMusicalSettingsToPrompt()` (`logic.ts`) replaces every prose span of a field, back to front so offsets stay valid, in the *original notation* (`renderKey`/`renderMusicalPhrase`: note-name case, `♯♭` vs `#b`, spacing, English/katakana/kanji quality word and its capitalization; `キーはE♭マイナー` -> `キーはF♯メジャー`), and only a field the prompt states nowhere goes into the managed line. The read-back round trip is pinned in `tests/logic.test.ts`. Clearing a dropdown never deletes prose (that would break the sentence around it); it only drops the field from the managed line, and the dropdown shows the still-stated value again (see the next bullet). The bare Japanese phrase `C長調` (no `キー` prefix) is *not* detected - that is a pre-existing pattern limit, not something the span work changed. `applyMusicalSettings()` (`logic.ts`) is only the writer of the extension-managed `Musical settings:` line, called by `applyMusicalSettingsToPrompt()` when the managed content really changes. **The managed line is authoritative per field, not per line** (`detectMusicalSettings()`): a line stating only the key must not hide a tempo the prose states, because that prose is now edited. For a field stated in *both* places - which a prompt written by an older build can contain - the managed line stays authoritative and the prose is left alone; new code paths never create that duplication, and it is deliberately not cleaned up. `SunoController.selectStyle()` merges musical fields field-by-field: explicit values in the newly selected style win, while fields absent from it retain the current unambiguous value; a style that states a field *ambiguously* (conflict) keeps that field untouched (`musicalSettingsForStyle()`), since carrying the current value in would rewrite the style's own phrases. Phrases the style already states are written as-is, so a style stating all three gets no managed line. `deriveStyleSelection()` compares saved styles through `musicallyComparable()` (managed line removed, every prose key/tempo/meter phrase replaced by a per-field placeholder), so a style whose key was rewritten stays selected and `{{STYLE}}` does not fall to カスタム; the accepted cost is that saved styles differing only in key/tempo/meter can match each other (the current selection is tried first). Its mastering-edit recovery splits by *line count* and keeps the leading block as typed, so a rewritten phrase is not rolled back to the saved wording. `SunoController.applyMusicalSettings()` works from the *current textarea text*, not the cached `baseStyle` (which can be stale, and is `''` for a legitimately empty base - an earlier `this.baseStyle || ...` fallback treated that as "unknown" and duplicated the mastering when the Style was unselected and only a mastering was selected). `splitMasteringPrompt()` (`logic.ts`, shared with `deriveStyleSelection()`) recognizes a mastering only when the text equals it or ends with it on its own line, and only that recognized mastering is composed back, so a stale selection is never re-appended. The musical phrases are rewritten in the base alone and the result is composed *before* the mastering, preserving the invariant that mastering remains the final line and that mastering text itself is never rewritten. `composePrompt()` trims only the Style's trailing whitespace, and `applyMusicalSettings()` only appends the managed line when none exists yet, so the *first* managed-line insertion preserves the Style's leading and internal whitespace. Rebuilding or removing an *existing* managed line (a later dropdown change once the line is there) deliberately keeps the older trim + blank-line-collapse behavior, so it can still normalize that whitespace. The native selects use `field-sizing: content` as progressive enhancement with min/max inline constraints; their key width must fit the longest key label and their meter width must fit a selected signature plus its arrow, while their fallback remains usable without excess space in supporting browsers. `MusicalSettingsControls` renders inside the single `StyleControls` host rather than a neighboring Shadow host, so the orange outline and hover feedback cover the full combined card. The only status line is the conflict message (`ui.musicalSettingsConflict`): it is the one thing the dropdowns cannot say, because a conflicted field looks unselected, and it tells the user that choosing a value rewrites every conflicting phrase. An earlier line echoing the detected values (`D Minor · 92 BPM`) was removed as a pure repeat of the dropdowns; an initially empty Style prompt is neutral and must not announce a failed detection. Its fieldset has an accessible `aria-label` but no visible legend, while each field retains its visible label. Cover-origin traversal is intentionally not implemented until a stable, visible native source link has been confirmed; do not infer an original song from title text or use a private API.
  - **There is no Apply button: every dropdown change goes straight through `SunoController.applyMusicalSettings()`.** It rewrites the phrase the Style already states, or - for a field the Style states nowhere - adds it to the managed line as soon as the value is chosen (the removed `applyMusicalSettingsLive()` used to gate on "already stated"; that gate was dropped because `onChange` only fires on a deliberate choice, so it cannot invent text on its own). It returns without writing while `isExecutingCreate` is set, and when no Style textarea is mounted at all, because `setStylePrompt()` would otherwise click the Style disclosure open. In the current DOM dumps (`docs/showless.txt`) the Style textarea stays in the DOM inside an `aria-hidden`, `height: 0` container while collapsed, so the no-textarea case should be rare; it was not confirmed for every state.
  - **The dropdowns are controlled by the detected value** (`state.musicalSettings`), never by local drafts, so they cannot show something the Style text does not say: a declined write (Create running, no textarea, over the 1,000-character limit) or clearing a field whose phrase is stated in prose (prose is never deleted) just snaps the dropdown back. A detected key or meter the pickers do not list (`Cb Major`, `E# Minor`, `11/16`, ... - the detector recognizes more than `MUSIC_KEYS`/`TIME_SIGNATURES`) is added as a temporary option by `withDetectedOption()`, because a controlled select cannot show a value it has no option for; it disappears once the text states something else, and the detection regexes were deliberately not widened. Only the tempo, which is free-typed, keeps a draft; it is committed on `onBlur` and on Enter (`commitTempo()`), never per keystroke (typing `160` must not write `16`), and skipped when it equals the detected value. `commit()` overlays *only the field the user just changed* on `controller.getState().musicalSettings`; an earlier version built the call from local drafts and an E2E caught it reverting tempo/meter to stale values right after a saved style was selected. `tests/e2e/extension.spec.ts` pins the Enter commit, the blur commit, "typing writes nothing", and the snap-back.
- **`SunoAdapter.sidebarPlacement()` only accepts *visible* anchors.** `a[href="/hooks"]` exists on the live site but only inside the mobile bottom nav (`display: none` on desktop, zero-size rect), so taking the first DOM match put the gear in an element that never rendered. Candidates in order: visible `/hooks` link, visible profile split row (`beforebegin`), visible nav container (`beforeend`); `tests/adapter.test.ts` pins the hidden-hooks case.
- Keep all host-page selectors in `src/suno/adapter.ts`. Prefer stable data attributes, accessible labels, placeholders, and relative structure over CSS classes.
- Suno is a React SPA. Update controlled host inputs through native property setters followed by bubbling `input` and `change` events.
- Never access private Suno APIs, cookies, or page-framework state. Suno's own saved styles are read only from the visible native dialog and are never persisted by the extension - only the extension's own custom style list (below) is.
- **The style dropdown shows a merge of two independent sources, controlled by `StyleSource` (`'merged' | 'custom' | 'suno'`, stored as `styleSource` and defaulting to `'merged'`).** `SunoController` keeps them apart internally - `private sunoStyles: SavedStyle[]` (from `adapter.extractSavedStyles()`, cache-only, never persisted) and `private customStyles: CustomStyle[]` (from `chrome.storage.local`, CRUD via `saveCustomStyle()`/`deleteCustomStyle()` in `src/storage/repository.ts`, structurally identical to `MasteringPrompt`) - and `private applyStyleSources()` recomputes `state.styles = mergeStyleSources(customStyles, sunoStyles, styleSource)` (`src/domain/logic.ts`) into the single merged list every downstream consumer (`StyleControls`, `deriveStyleSelection()`, take-history `styleName`, `{{STYLE}}`) reads - none of them are aware of the split. Custom entries sort first, so a custom style and a Suno style sharing the same prompt resolve to the custom one. **`SunoController.loadStyles()` must never call `adapter.extractSavedStyles()` while `state.styleSource === 'custom'`** - opening Suno's native saved-styles dialog at all would defeat the point of that mode; it takes an early-return branch that only merges the already-known `customStyles`. Custom style ids come from `crypto.randomUUID()` while Suno style ids come from `savedStyleId()` (index + name + prompt prefix), so the two id spaces can never collide. A custom style edited/deleted out from under a live selection is caught the same way a deleted mastering/preset is - in `initialize()`'s `subscribeStorage` callback and in `setStyleSource()` - by checking `state.style` is still a member of the freshly-merged `state.styles`; if not, `state.style` clears to `isCustomStyle: true` (the Style *text* is left untouched, matching how a deleted mastering/preset already behaves). The gear button on the styles row (`ui.aria.editStyles`) opens `openSettings('styles')`, a new `SettingsSection` edited with the same add/edit/delete form pattern as the `masterings` section in `SettingsDialog.tsx`, plus a `<select>` for `styleSource` at the top of that section.
- When reading a saved-style row, extract only its leaf prompt text. The row also contains the style name and saved date; they are metadata for the dropdown and must never be written into Suno's Style field. `tests/adapter.test.ts` covers this nested-span layout.
- **Style-owned Exclude:** `CustomStyle`/`SavedStyle` have optional `excludedStyles`. `undefined` leaves the live Exclude field unchanged; an explicit empty string clears it. Suno-derived styles never set this field. `selectStyle()` writes the prompt first, then applies a saved Exclude and reports a skipped write as partial application. `syncSelectionFromStyleText()` also passively compares the visible Exclude when a selected custom style saved one, so manual edits make the style custom and reverting restores it. The Style-row bookmark uses `captureStyleForSave()` to prefill the form from the current base style (only a recognized trailing mastering line is omitted) and Exclude when it is readable. `presetOptionKeys` intentionally omits Exclude; schema v2→v3 removes it from option presets, but take-history snapshots retain it so `reuseTake()` continues to restore it.
- Content UI is mounted in a Shadow DOM and must not use untrusted text as HTML.
- **Mounting survives Suno's re-renders by moving hosts, not recreating them.** `src/content/mount.ts`'s `createMounter()` keeps one `<suno-create-assistant>` host (and its React root) per key for the life of the page; when Suno's reconciliation deletes or displaces a host, the mounter moves the *same* host back into place via `insertAdjacentElement` instead of unmounting/remounting React. `Mounter.reattach()` runs synchronously inside the `MutationObserver` callback in `entrypoints/suno.content.tsx` (before the debounced `refreshMounts()`), so a deleted host reappears before the next paint instead of flickering. Do not reintroduce the old pattern of tearing down and recreating the host on every anchor change.
- `SunoAdapter.observeForm()` deliberately does **not** filter out mutations caused by the extension's own hosts. A `MutationRecord` cannot distinguish "we just moved this host" from "Suno deleted it," and the latter is exactly the case `reattach()` must react to. This is safe because `reattach()`/`mount()` are idempotent (a correctly-placed host triggers no further DOM change), so the self-triggered pass terminates after one cycle. If you're tempted to add a self-mutation filter here again, don't — see `tests/adapter.test.ts`'s "notifies the listener when its own host is removed" case, which exists specifically to catch a regression of this.
- Both the Style control and Preset control anchor to the persistent header rows of their respective disclosures (`SunoAdapter.styleAnchor()` → `styleHeaderRow()`, `optionsAnchor()` → `optionHeaderRow()`), so they stay visible inside Suno's cards whether the disclosures are expanded or collapsed. If `optionHeaderRow()` cannot find a heading, `mount.ts`'s thrash detector (>8 reattachments within 2s) trips `onThrash('presets')` in `entrypoints/suno.content.tsx`, which falls back to placing the presets control directly above the title input (`titleAnchor`, `beforebegin`) for the rest of that page session.
- **`SunoAdapter.extractSavedStyles()` must click the *real* saved-styles trigger - two buttons share the same aria-label (confirmed live on suno.com/create, ja UI, 2026-09-20).** The real one is the Base UI dialog trigger (`aria-haspopup="dialog"`, `data-base-ui-click-trigger`, id `base-ui-_r_..._`) and opens a dialog with `aria-label="保存したスタイル"`. The other is a look-alike chip (`hxc-btn-variant-standard-legacy`, no `aria-haspopup`) inside the horizontally-scrolling style-tag strip; it opens a *different* dialog with **no `aria-label`** (named via `aria-labelledby` only) that also carries an extra "閉じる" button. The old code picked whichever was first visible in DOM order and looked the dialog up by aria-label only, so the chip path left an unmatched dialog visible (the suppressor CSS also matched by aria-label) and returned an empty list - the reported "dialog flashes, then the dropdown only shows 未選択" intermittent failure. `savedStylesTrigger()` now prefers the real trigger; `savedStylesDialog()` also matches via `aria-labelledby` text; `openAndReadSavedStyles()` additionally treats any `[role="dialog"]` that appeared after the click (`newDialogSince()`) as the target and hides every non-preexisting dialog while reading. Row buttons exclude `削除`/`削除: <name>`/`名前を変更`/`グリッド表示`/`閉じる` and English equivalents (`SAVED_STYLE_ACTION_LABEL`).
  - Other measured facts: the list renders within ~150ms of opening (70 buttons for 23 styles: each row has a full-row overlay button + rename + delete); clicking the real trigger while open closes it immediately; Escape on the dialog also closes it. A row's prompt is its `line-clamp-2` leaf span; the "7d" age label does not match the date regex but is always shorter than the prompt, so the longest-leaf rule still picks the prompt.
  - Defensive layers kept on top of that: `waitForSavedStyleRows()` waits for a non-empty, stable row count (`SAVED_STYLES_TIMEOUT_MS`); the open -> read -> close cycle retries `SAVED_STYLES_ATTEMPTS` times (a missing dialog gives up after `SAVED_STYLES_OPEN_TIMEOUT_MS`); `closeSavedStylesDialog()` re-queries the trigger and falls back to Escape. `SunoController.refreshStyles()` shares one in-flight promise (`stylesRefresh`) since the dialog toggle is not re-entrant. `tests/adapter.test.ts`'s "extractSavedStyles races" block pins all of this, including a two-trigger fixture.
- **The Style/Mastering dropdown selection is derived from the Style textarea's current text, not from which control was used last.** `deriveStyleSelection()` (`src/domain/logic.ts`) is the single source of truth, called from `SunoController.syncSelectionFromStyleText()`: (1) the mastering stays selected only while the text still ends with `\n<mastering prompt>` (or equals it) - if the user edited/deleted that text it drops to 未選択 and `{{MASTERING}}` follows, **but the style is kept** when the selected style's prompt is still the leading block of the text (only the mastering part changed), and the controller's `rememberedMastering` (last mastering the user applied) is re-selected as soon as the text matches it again, so undoing the edit restores both dropdowns; (2) the remaining base text keeps the selected style if it still equals its prompt, otherwise adopts any saved style whose prompt matches exactly (this is how Suno's "プロンプトを再利用" of a saved prompt is reflected), otherwise becomes "カスタム"; (3) empty base text is 未選択, **not** カスタム. It runs from the `input` listener (`force`) and from `reconcile()` (every debounced DOM-mutation cycle) so a text change that fires no `input` event is still noticed - `reconcile()` only acts when the text differs from `lastStyleText` (last text the extension wrote or reconciled), so pre-existing text at page load is baselined rather than labelled カスタム. It is skipped when no Style textarea is mounted (a closed disclosure would otherwise read as "field cleared"). Whether Suno's own prompt reuse actually fires `input` and mutates the DOM was not verified live (it would overwrite the user's draft); the `reconcile()` path is the safety net for the no-event case, relying on the Style header row's prompt preview changing.
- **`SunoController.handleStyleInput()` must never write to Suno synchronously - it defers its whole reaction (`pendingStyleSync`, `setTimeout(0)`) - confirmed live on suno.com/create.** The listener is registered on `document` in the capture phase, so it runs *before* Suno's React has handled the same keystroke. `updateAutoTitle()` -> `setTitle()` dispatches `input`/`change` on Suno's title input; when the title value actually changes (e.g. the style name flips to カスタム), Suno re-renders with the Style textarea's pre-keystroke state, which reverts the typed character and moves the caret to the end ("can't edit the middle of the text"). Measured: inserting a character mid-text with a synchronous title write left the text unchanged with the caret at the end; the identical write one tick later inserted normally. It is not caused by the dropdowns re-typing the text (the only Style-textarea writer is `writeStyle()`, used by select/clear). Any new work added to this listener that touches the Suno DOM must stay behind that deferral; `tests/controller.test.ts` pins "does not write the auto title synchronously inside the input event".
- **The preset dropdown follows the live "その他のオプション" values the same way (`SunoController.syncPresetFromOptions()`, called from `reconcile()`).** A preset stays selected only while every field it stores still matches (`optionFieldsMatch()` in `src/domain/logic.ts`: exact for sliders/toggles/max mode, trimmed for excluded styles, seconds only for a custom duration, `personalization.enabled` only). When a stored field is changed by hand it turns into `isCustomPreset` (label カスタム, `{{PRESET}}` in the title becomes カスタム, no preset id in take records), and `rememberedPreset` re-selects it when the values match again. Deliberately *not* mirrored from the style logic: there is no "adopt any other preset that happens to match", because a preset storing only a few fields would match constantly. Nothing happens if no preset was ever applied (initial values are not labelled カスタム).
  - It reads through `SunoAdapter.peekOtherOptions()`, **not** `readOtherOptions()`: the latter clicks the disclosure open/closed when collapsed, which is unacceptable on every reconcile pass. `peekOtherOptions()` returns `undefined` while the controls are not visible (so nothing is synced while the disclosure is collapsed; it catches up on the `aria-expanded` mutation when reopened). Both share `readOptionControls(panel)`.
  - `isApplyingOptions` suppresses the sync while `applyPreset()`/`reuseTake()` are stepping through fields (mid-apply values legitimately don't match yet); `presetIgnoredKeys` = the last apply's `skipped` fields plus any `unreadable` field, which are never held against the preset. After `reuseTake()` the preset naturally flips to カスタム unless the values still match.
  - `observeForm()`'s `attributeFilter` now includes `aria-valuenow` and `data-selected`; confirmed live that a slider arrow-key step and a toggle click each produce those attribute mutations (previously nothing reached `reconcile()` for a manual slider/toggle change). The stored preset object is also re-resolved by id on every storage change, so edits made in the settings dialog are picked up.
- Keep the host-page inspiration-label shortening and Create-button lookup in `src/suno/adapter.ts`. `triggerCreate()` matches create buttons in `<main>` even when containing credit badges ("作成 10", "Create", etc.) and excludes navigation links. The Suno page content script listens for `Cmd + Enter` (macOS) / `Ctrl + Enter` (Windows/Linux) directly. There are no Manifest `commands` or background workers.
- **Preset creation and editing use one direct-value form in `SettingsDialog.tsx`.** The "設定を保存" button next to the preset dropdown opens the dialog and automatically captures Suno's live values into the creation form; there is no capture button inside the dialog. "編集" starts from `OtherOptionsPreset.fields` without rereading Suno, so saving cannot silently overwrite a preset with unrelated live values. A checkbox includes/excludes each key, and its native controls edit the saved value. Keep this distinction when changing the UI or tests.
- **`SettingsDialog.tsx` is a sidebar-tabbed layout (`.suno-assistant__dialog-layout` = nav + content), not one long scrolling page.** `SECTION_ORDER` (`['display', 'lyricsTags', 'styles', 'masterings', 'presets', 'titleFormat', 'takeHistory', 'backup', 'about']`) fixes the tab order; `activeSection` (`state.settings?.section ?? 'titleFormat'`) decides which single `<section>` renders in `.suno-assistant__dialog-content` - every other section is unmounted, not just visually hidden. The dialog widened to `min(880px, 100vw - 32px)` to fit this (`@media (max-width: 640px)` collapses the sidebar into a horizontally-scrolling tab row above the content). Only the header stays fixed; the nav and content panes scroll independently of each other.
  - Because only the active section is mounted, any state a section-switch depends on (e.g. `presetForm`) must be set *before* navigating to a different tab, or reset by whatever effect owns it - see `SettingsAction`'s `'reuse-as-preset'` below for the concrete case this bit.
  - `saveTakeAsPreset()` (テイク履歴's "プリセットとして保存") opens the presets tab and pre-fills `presetForm` directly, without the "設定を保存" capture flow. It passes the `'reuse-as-preset'` `SettingsAction` specifically so the section-change effect (which otherwise clears `presetForm` whenever the presets tab is entered without `action === 'create-preset'` - e.g. via its own sidebar tab or the gear icon beside the preset dropdown) does not immediately wipe the just-set form back out. If you add another way to pre-fill `presetForm` from outside the dialog, it needs its own `SettingsAction` value too, not a reuse of `'create-preset'` (that would incorrectly re-trigger the live-Suno capture) or no action at all (that hits the same wipe).
- **The style/mastering/preset dropdowns no longer carry a "管理…"/"Manage..." menu item.** Opening the settings dialog on their section (`openSettings('styles')` / `openSettings('masterings')` / `openSettings('presets')`) is instead done via a dedicated gear-icon button placed at the right edge of each row (`.suno-assistant--styles` / `.suno-assistant--presets`), styled identically to `LyricsTagPalette`'s own settings gear (`GearIcon` in `src/content/components.tsx`, `.suno-assistant__tag-button.suno-assistant__tag-button--settings`). The styles row's gear (`ui.aria.editStyles`) opens the `styles` section (custom style list + the `styleSource` dropdown-merge setting), not `masterings` - mastering prompts get to their own section via the sidebar tab list instead, one click away. `.suno-assistant__settings-button { margin-left: auto }` pushes it to the row's right edge regardless of how wide the dropdown/buttons before it are. `MenuItem`/`Dropdown` in `components.tsx` no longer support a `manage` entry - if you need another dropdown-triggered dialog action in the future, add a dedicated button next to it rather than reintroducing an in-menu item.
- **The styles row's "解除" (clear) and the presets row's "設定を保存" (save preset) buttons are icon-only, right-aligned next to their row's gear button, paired more tightly than the row's own 8px gap.** `StyleControls`' clear button uses `TrashIcon`; `PresetControls`' save button uses `BookmarkIcon` (both in `src/content/components.tsx`).   - `src/locales/index.ts`: Locale registry (`SUPPORTED_LOCALES`), language detection (`detectLanguage()`), getters (`getLocale()`, `getHostLocale()`, `getUiMessages()`), and cross-locale fallback query helpers (`getAllTitlePlaceholders()`, `getAllOptionResetLabels()`, `getAllSavedStyleTriggerLabels()`, `getAllSavedStyleMutationLabels()`, `getAllSavedStyleSaveNewLabels()`, `getAllClearFormLabels()`, `getAllClipRowLikeLabels()`, `getAllClipRowShareLabels()`, `getSliderLabels()`, `getRowLabels()`). `SunoController.handleDocumentClick` uses these (not hardcoded Japanese) to detect a saved-style mutation or Suno's own "Clear all form inputs" click regardless of UI language — don't reintroduce a language-specific string literal there.
- **Language detection**: `detectLanguage()` inspects `document.documentElement.lang` (e.g. `'ja'`, `'en-US'`) or `document.documentElement.dataset.language`, falling back to `'ja'`.
- **Hybrid fallback architecture for host DOM queries**: `SunoAdapter` queries using the detected host locale (`this.hostLocale`), but also leverages aggregated cross-locale patterns (e.g. searching all known title placeholders or reset labels) when inspecting inputs or headers. This guarantees that host controls can be found even during asynchronous language switches, hydration delays, or when Suno renders mixed-language strings.
- **Extension UI localization**: Content script components (`src/content/components.tsx`, `SettingsDialog.tsx`) and the controller (`src/suno/controller.ts`) retrieve localized copy via `getUiMessages(this.lang)`.
- **Confirmed English host DOM specifics (from `docs/alldom_en.txt`)**:
  - "その他のオプション" disclosure heading is **`More Options`** (not "Other Options"), and its reset action is `Reset All`.
  - Styles heading is `Styles` (with child `<div>Styles</div>` followed by prompt text); Lyrics heading is `Lyrics`.
  - Title input placeholder is `Song Title (Optional)`.
  - Excluded styles placeholder is `Exclude styles`.
  - Sliders `aria-label`: `Weirdness`, `Style Influence`, `Variety` (variation), `Audio Influence`.
  - Toggle button rows: `Vocal Gender` (`Male`, `Female`), `Duration` (`Custom`, `Auto`), `Max Mode` (`On`, `Off`), `Personalize` (`On`, `Off`, `My Taste`).
  - Saved Styles: trigger `aria-label="View saved style prompts"`, dialog `aria-label="Saved Styles"`, action buttons (`Delete`, `Rename`, `Grid View`) excluded from leaf prompt extraction. Suno's own "Save prompt" button (adds a new saved style directly from the style textarea) is `aria-label="Save prompt"`.
  - Suno's own "Clear all form inputs" action is `aria-label="Clear all form inputs"` (confirmed in `docs/alldom_en.txt`; do not assume a shorter "Clear all" or "Clear form").

- **Adding a new language**:
  1. Create `src/locales/<lang>.ts` implementing `LocaleDefinition` (`host` and `ui`).
  2. Add the language code to `SupportedLanguage` in `src/locales/types.ts`.
  3. Register the definition in `SUPPORTED_LOCALES` in `src/locales/index.ts`.
  4. Add unit test assertions in `tests/locales.test.ts`.

## Storage

`chrome.storage.local` holds schema version 3 (`CURRENT_SCHEMA_VERSION` in `src/domain/models.ts`): mastering prompts, eight-field option presets, the Auto title preference, title format, take numbers, disclosure preference, lyrics tags, `customStyles` (with optional per-style Exclude), `styleSource`, and take history. Migration v2→v3 removes `optionPresets[].fields.excludedStyles` but intentionally keeps `takeHistory[].options.excludedStyles` for take reuse. Tab-local selection state and Suno's own saved-style cache (`sunoStyles`, unlike `customStyles`) must remain ephemeral.

- **`src/storage/repository.ts`'s `migrate()` upgrades an older stored value step by step (one entry per version in `migrations`, keyed by the version it upgrades *from*) and deliberately passes a *newer*-than-current value through unchanged rather than resetting it to defaults.** This matters because `readStorage()` used to treat anything but an exact `schemaVersion === 1` match as unreadable and silently reset the user's whole configuration — a real risk the moment a second schema version shipped. If you add a new schema version: add one migration step (old shape in, new shape + version out, never dropping a field), bump `CURRENT_SCHEMA_VERSION`, and do not touch the "future version passthrough" behavior in `migrate()`/`isKnownStorageShape()` — it is what protects a newer install's data from an older build of the extension (or a plain downgrade) reading it.
- **Export/Import (`SettingsDialog.tsx`'s "バックアップ" / "Backup" section) is a full-replace, not a merge.** `exportBackup()` returns the live `readStorage()` result (optionally with `takeHistory` zeroed out via its `includeTakeHistory` argument) as a downloadable JSON file; `parseBackup()` runs the same `migrate()` path so an export from an older build of the extension is upgraded on import rather than rejected or written back stale. There is intentionally no merge logic — resolving id/name collisions between the current and imported data was judged not worth the complexity for a personal-backup feature. All communication stays local (`Blob`/`URL.createObjectURL`, a `<input type="file">` read via `FileReader`/`File#text()`); nothing is ever sent anywhere.
- **`updateStorage()`/`replaceStorage()` serialize every storage mutation through a single module-scoped `writeQueue` promise, rather than each caller doing its own independent `readStorage()` → mutate → `writeStorage()`.** Without this, two callers racing a read-modify-write cycle — most realistically `SunoController.executeCreateWithTake()`'s `appendTakeRecord()` (fired on every Create submission) against `clip-linker.ts`'s `linkTakeToClips()` (fired on every `refreshMounts()` cycle by `syncClipButtons()` in `entrypoints/suno.content.tsx`, which runs on essentially every DOM mutation) — could both read the same pre-write snapshot and then each write back their own version, silently discarding whichever finished last (a fresh take-history record disappearing, or a clip-id link never landing). Chaining every mutation onto `writeQueue` forces each caller's own `readStorage()` to wait until the previous caller's `writeStorage()` has actually resolved, closing that window entirely; a rejected mutation is caught on the queue itself (not on the promise returned to its caller) so one failure can't permanently wedge every mutation queued after it. `tests/storage.test.ts`'s "concurrent storage writes" block pins this down by first reproducing the lost-update with `Promise.all([...])` against the unserialized code, then asserting it no longer happens. If you add a new storage-mutating function, route it through `updateStorage()` (or chain it onto `writeQueue` the same way `replaceStorage()` does) — a function that calls `writeStorage()` directly reopens this race.
- **`EXPECTED_CLIPS_PER_TAKE` (`src/domain/models.ts`) is deliberately capped at 2 and is a single source of truth shared by `storage/repository.ts`'s `findUnlinkedTakeRecords()` (which record still counts as pending) and `suno/clip-linker.ts`'s `linkPendingTakes()` (how many clips one record can claim).** It used to be defined independently in each file (`clip-linker.ts`'s own constant vs. a hardcoded `< 2` in `repository.ts`), which is a drift risk if only one were ever changed. This is a known, accepted boundary, not an oversight: once a record reaches 2 linked clips it is treated as fully linked and `findUnlinkedTakeRecords()` stops offering it fresh matches, so a hypothetical third same-title clip appearing in a *later* `linkPendingTakes()` pass will not be attributed to it (see the "claims only EXPECTED_CLIPS_PER_TAKE clips per record..." test in `tests/clip-linker.test.ts`, which pins this exact boundary). There is no confirmed evidence Suno ever generates more than 2 clips for one submission — if that changes, revisit both the constant and `findUnlinkedTakeRecords()`'s eligibility check together, not just the per-pass claim limit in `clip-linker.ts`.
