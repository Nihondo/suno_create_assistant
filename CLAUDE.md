# Suno Create Assistant development notes

## Stack and commands

This is a Manifest V3 Chrome extension built with WXT, React, TypeScript, and pnpm.

Permissions are `['storage']` only. There is no `tabs` permission, no background service worker, and no options page: all styling, presets, mastering management, and keyboard shortcuts run purely in the content script inside the Suno tab itself.

Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e`, and `pnpm build` before handoff. The unpacked build output is `install/chrome-mv3`.

`tests/e2e/extension.spec.ts` starts a local HTTPS fixture mapped to `suno.com` only inside Playwright Chromium. Install its browser with `pnpm exec playwright install chromium`; the E2E test does not contact Suno.

## Suno integration rules

- Run the content script only on `https://suno.com/create*`. The settings dialog host is mounted unconditionally; the styles/presets/title controls only mount while the Advanced tab is active.
- Keep all host-page selectors in `src/suno/adapter.ts`. Prefer stable data attributes, accessible labels, placeholders, and relative structure over CSS classes.
- Suno is a React SPA. Update controlled host inputs through native property setters followed by bubbling `input` and `change` events.
- Never access private Suno APIs, cookies, or page-framework state. Saved styles are read only from the visible native dialog and are never persisted by the extension.
- When reading a saved-style row, extract only its leaf prompt text. The row also contains the style name and saved date; they are metadata for the dropdown and must never be written into Suno's Style field. `tests/adapter.test.ts` covers this nested-span layout.
- Content UI is mounted in a Shadow DOM and must not use untrusted text as HTML.
- **Mounting survives Suno's re-renders by moving hosts, not recreating them.** `src/content/mount.ts`'s `createMounter()` keeps one `<suno-create-assistant>` host (and its React root) per key for the life of the page; when Suno's reconciliation deletes or displaces a host, the mounter moves the *same* host back into place via `insertAdjacentElement` instead of unmounting/remounting React. `Mounter.reattach()` runs synchronously inside the `MutationObserver` callback in `entrypoints/suno.content.tsx` (before the debounced `refreshMounts()`), so a deleted host reappears before the next paint instead of flickering. Do not reintroduce the old pattern of tearing down and recreating the host on every anchor change.
- `SunoAdapter.observeForm()` deliberately does **not** filter out mutations caused by the extension's own hosts. A `MutationRecord` cannot distinguish "we just moved this host" from "Suno deleted it," and the latter is exactly the case `reattach()` must react to. This is safe because `reattach()`/`mount()` are idempotent (a correctly-placed host triggers no further DOM change), so the self-triggered pass terminates after one cycle. If you're tempted to add a self-mutation filter here again, don't — see `tests/adapter.test.ts`'s "notifies the listener when its own host is removed" case, which exists specifically to catch a regression of this.
- Both the Style control and Preset control anchor to the persistent header rows of their respective disclosures (`SunoAdapter.styleAnchor()` → `styleHeaderRow()`, `optionsAnchor()` → `optionHeaderRow()`), so they stay visible inside Suno's cards whether the disclosures are expanded or collapsed. If `optionHeaderRow()` cannot find a heading, `mount.ts`'s thrash detector (>8 reattachments within 2s) trips `onThrash('presets')` in `entrypoints/suno.content.tsx`, which falls back to placing the presets control directly above the title input (`titleAnchor`, `beforebegin`) for the rest of that page session.
- Keep the host-page inspiration-label shortening and Create-button lookup in `src/suno/adapter.ts`. `triggerCreate()` matches create buttons in `<main>` even when containing credit badges ("作成 10", "Create", etc.) and excludes navigation links. The Suno page content script listens for `Cmd + Enter` (macOS) / `Ctrl + Enter` (Windows/Linux) directly. There are no Manifest `commands` or background workers.
- **Preset creation and editing use one direct-value form in `SettingsDialog.tsx`.** The "設定を保存" button next to the preset dropdown opens the dialog and automatically captures Suno's live values into the creation form; there is no capture button inside the dialog. "編集" starts from `OtherOptionsPreset.fields` without rereading Suno, so saving cannot silently overwrite a preset with unrelated live values. A checkbox includes/excludes each key, and its native controls edit the saved value. Keep this distinction when changing the UI or tests.
- `SunoAdapter.readOtherOptions()` returns `OtherOptionsCapture { snapshot, unreadable }` rather than failing outright when one control can't be found: each of the 9 fields (`excludedStyles`, `vocalGender`, `duration`, `maxMode`, `weirdness`, `styleInfluence`, `variation`, `audioInfluence`, `personalization`) is read independently, and only the ones whose row/slider/input is missing are added to `unreadable`. `optionPanelAndHeading()`/`optionControlsVisible()` locate the panel via `PANEL_MATCHERS`, staged from most to least specific (both known sliders → any slider → any known settings row), so a single relabeled control no longer fails the whole capture. `SettingsDialog` disables the checkbox for any key listed in `unreadable` and shows `describeSkipped()` of them as a notice.
  - `audioInfluence` ("オーディオの影響" / "Audio Influence") is only present once an audio reference (upload/remix) is attached to the create form, so it legitimately lands in `unreadable` the rest of the time — that is not a bug to "fix" by making it required.
- `optionHeading()` excludes any element inside `[data-testid="clip-row"]` before matching on text/aria-label. Each row in the workspace clip list has its own "その他のオプション" / "More options" context-menu trigger button with the *exact same* aria-label as the "More Options" disclosure heading (confirmed in `docs/alldom_ja.txt`, `docs/alldom_en.txt`, `docs/showmore.txt`). Without the exclusion, `optionHeading()`'s `.at(0)` only happens to pick the right element because the create form currently precedes the clip list in document order — an implementation detail, not a contract. `tests/adapter.test.ts`'s "ignores a workspace clip row's own..." case pins this down by deliberately placing the clip-row button first in the fixture.
- **Confirmed production DOM facts (verified via a live-site console dump, not assumed)** — check these before "fixing" a selector back to something that only looks more idiomatic:
  - The "その他のオプション" disclosure trigger is `<div role="button" tabindex="0" aria-expanded="...">`, **not** a `<button>`. `optionHeading()` matches `'button, [role="button"]'` for exactly this reason; don't narrow it back to `button` alone.
  - Its "すべてリセット" action *is* a real `<button aria-label="すべてリセット">`.
  - The row toggle buttons (男性/女性, カスタム/Auto, オン/オフ, etc.) are real `<button>` elements, but selection is conveyed via `data-selected="true"/"false"`, not a class name — `hxc-btn-variant-standard` (still used as a last-resort fallback in `selected()`) was already stale at the time this was checked. If presets ever silently misjudge which toggle is active again, check `data-selected` first, not the class list.
  - A plain `.click()` on a row toggle button (e.g. 女性) does correctly flip its `data-selected`, confirmed directly on the live site. Applying a preset failing to change toggle values is not a click-delivery problem; see the next point.
- **`applyOtherOptions()`/`setSlider()` re-fetch the panel/slider fresh for every single field/step — never reuse one captured reference across multiple mutations.** Two things confirmed directly on the live site, both root-caused to the same underlying behavior (Suno can replace the entire options subtree in reaction to a single click or keystroke):
  - *Toggle fields silently no-oping after the first one that actually changed something* ("プリセットを選択しても、値が設定されない"): with one `panel` reference reused across `vocalGender`/`duration`/`maxMode`/`personalization`, the first field's click could make Suno replace the whole subtree, leaving every later field's `rowButton()` lookup resolving inside a detached copy - `.click()` on a detached element never bubbles to Suno's listeners. Fixed by calling `optionPanel()` again immediately before each field's own DOM interaction.
  - *A slider only moving by 1 no matter how many steps are requested* ("プリセットを選択するたびに、1%ずつ動いたりする"), confirmed by firing 5 `ArrowRight` keydowns in a tight synchronous loop (moved by 1) vs. the same 5 keydowns each separated by a `requestAnimationFrame` yield (moved by 5, exactly as expected). `setSlider()` now re-queries the live slider and its current `aria-valuenow` before every single keydown and awaits `settle()` (one rAF) after each one, up to `SLIDER_STEP_GUARD` (200) steps. Do not go back to computing the step count once up front and firing that many keydowns in a row.
  - Both `applyOtherOptions()` and `SunoController.applyPreset()` are therefore `async`; `applyPreset()` shows a `'適用しています…'` notice immediately so the UI doesn't look stuck.
- **Setting a slider by double-clicking its "NN%" readout and typing into the revealed `<input type="text">` was tried, reverted, then retried and confirmed working — but only when the typed value is committed with a real `Enter` keypress.** History, in order:
  1. An early attempt double-clicked the readout, typed a value, and read `aria-valuenow` straight back **without ever pressing Enter**. It looked like a great speedup and even verified correctly in isolated live-site testing (`aria-valuenow` held the typed value for a full second with nothing else touched) - but it turned out to only write a transient DOM attribute, not Suno's real underlying state. The value silently reverted the moment anything else caused React to reconcile that region (in practice: `applyOtherOptions()` moving on to its next field, ~120ms later). `setSlider()` was changed to only step arrow keys as a result.
  2. **`Home`/`End`/`PageUp`/`PageDown` were tried as a cheaper alternative and confirmed to do nothing at all**: dispatching each as a `keydown` on a focused `[role="slider"]` left `aria-valuenow` completely unchanged, and a genuine physical keypress of the same keys just scrolled the surrounding page - Suno's slider component has no handler for them, full stop. There is no coarse-key shortcut.
  3. **The double-click path was retried, this time genuinely dispatching a real `Enter` keydown/keypress/keyup after typing the value - and confirmed manually on the live site that this commits Suno's real state**: double-click 奇抜さ's "NN%" readout, type a new value, press Enter, then click an *unrelated* toggle and wait ~1-2s - the slider's value held. This is the missing piece step 1 never tried. `SunoAdapter`'s `trySliderFastCommit()` implements this: double-click the slider's `nextElementSibling` readout (confirmed to always be positioned there, both before and after the swap to an `<input>` - not reachable by any stable class name, Suno's classes are hashed per build), set the revealed input's value via `nativeSetValue()`, dispatch a real Enter, then **re-check `aria-valuenow` matches the target afterward** before trusting it. `setSlider()` tries this first and falls back to the arrow-key loop on any failure (element/input not found, or the post-commit value doesn't match) - so a live-site surprise degrades to the slower, exhaustively-verified path instead of silently applying a wrong value. Only verified directly on 奇抜さ/Weirdness; the other three sliders share the same component so this is expected but not separately confirmed.
  - **If this stops working after a future Suno update**, don't reflexively reach for arrow-only again — first re-run the manual survival test above (dblclick → type → Enter → click something unrelated → wait ~1-2s → check `aria-valuenow`) to see whether it's `trySliderFastCommit()`'s DOM assumptions that broke (fixable) or Suno's actual commit behavior that changed (not fixable from here).

- **Theming does not read Suno's own CSS custom properties — it never worked.** `src/content/suno-ui.css` used to reference `var(--color-foreground-primary, #f5f5f6)` and similar guessed Suno variable names throughout. Those names were never confirmed and Suno apparently doesn't define them, so every one of those `var()` calls was silently always falling through to its hardcoded dark fallback, regardless of the page's actual theme - the extension's UI simply never followed Suno's light mode. Fixed by defining the extension's own tokens (`--sca-fg`, `--sca-bg-control`, etc.) on `:host` in `suno-ui.css`, overridden under `:host([data-theme="light"])`. `src/content/theme.ts`'s `detectSunoTheme()` determines the actual theme by reading the page's declared `color-scheme` or the perceived brightness of `document.body`'s/`document.documentElement`'s real computed background color - not by guessing Suno variable names again. `entrypoints/suno.content.tsx` calls it once per `refreshMounts()` cycle and passes the result as `createMounter().mount()`'s new `theme` parameter, which stamps `data-theme` onto each host. If you add a new color anywhere in this CSS, it must be one of these `--sca-*` tokens (or a new token following the same pattern) - never `var(--color-..., <hardcoded fallback>)` again.
- **`.suno-assistant`'s box (background, radius, padding, no border) and `--sca-fg`/`--sca-bg-card` are exact values measured with `getComputedStyle()` against Suno's own "スタイルを除外" row, not chosen freehand.** Suno's CSS class names are hashed per build (`css-xxxxx`), so they can never be targeted or reused as selectors - only measuring the *computed* values survives a rebuild. Measured directly: row text `rgb(16, 16, 18)` light / `rgb(247, 244, 239)` dark, row background the *reverse* of that pair, `border-radius: 12px`, `padding: 8px 16px`, no border. Suno swaps exactly those two colors between light/dark, which is why the token pairs mirror each other. The toggle buttons' `border-radius: 8px` (not a full pill) was measured the same way. If asked to match Suno's look again, re-measure with `getComputedStyle()` on a concrete reference element rather than eyeballing colors from a screenshot - guessed values (CSS variable names in the first pass, then freehand hex colors in the second) were wrong both previous times.
- **The presets row must not stretch to the full width of its parent "その他のオプション" card.** It renders as a standalone row there (not sharing a flex row with other controls, unlike the styles/mastering row), so `:host([data-suno-create-assistant="presets"]) { display: inline-block; width: auto; }` keeps it sized to its own content instead of a block element's default full-width behavior. Its `.suno-assistant` box itself uses the same sizing/coloring as every other row (see the point above) - it is not a separate, smaller, or stripped-down style.
- **Preset application success is silent (no redundant 'プリセットを適用しました。' notification).** Buttons and select triggers use `white-space: nowrap` and `flex-shrink: 0` so they never collapse or vertically wrap text. If any field was skipped or errored, feedback is displayed below the controls on its own line (`flex-basis: 100%`) without displacing or squeezing the buttons.
- **The Auto title control mounts with `beforeend` inside `SunoAdapter.titleControlAnchor()`, not the anchor's parent.** Verified on the live site: the title anchor is the rounded icon + input card row with `display: flex; flex-wrap: nowrap`; its parent instead stacks the separate title and destination cards. `titleControlAnchor()` sets the title card row to `flex-wrap: wrap`, and the title host uses `flex: 0 0 100%`, keeping Auto title inside the title card on its own line. Its `autoTitleEnabled` state is stored in `chrome.storage.local` and must be restored during `SunoController.initialize()` before the control mounts; retain E2E assertions for card containment, row placement, and reload persistence.
- **The preset editor's custom-duration label and number input stay on one horizontally centered row.** `label:has(input[type="number"])` otherwise makes number labels block-level, so keep the scoped `.suno-assistant__duration-seconds` override and its E2E geometry assertion.
- **The Create button click and shortcuts are hooked for `{{TAKE}}` placeholder replacement.** When the song title contains `{{TAKE}}`, `SunoController.executeCreateWithTake()` increments the take count in `chrome.storage.local` for the key (title minus `{{TAKE}}`), inputs the resolved take number via `nativeSetValue`, submits via `triggerCreate()`, and immediately reverts the title field back to the template with `{{TAKE}}`. `reconcile()` and `updateAutoTitle()` are guarded while `isExecutingCreate` is active so reactive re-renders cannot overwrite the take number before submission.
- **Audio title placeholder `{{AUDIO}}` resolves from the remix audio card.** When the song title format contains `{{AUDIO}}`, `autoTitle()` replaces it with the source track name extracted from the uploaded/remixed audio card via `SunoAdapter.getAudioTitle()`. `{{WORKSPACE}}` remains dedicated to the workspace destination and is never overwritten.
- **The sidebar settings button mounts in the Light DOM (`shadow: false`) with `display: contents` on `<suno-create-assistant>`.** This allows Suno's native Tailwind CSS classes (`hxc-btn-base`, `hxc-btn-variant-tertiary-legacy`, `text-foreground-tertiary`, `hover:text-foreground-primary`, etc.) and the sidebar collapse state (`group-data-[show-content=false]/sidebar:opacity-0`) to apply directly and seamlessly without breaking across Shadow DOM boundaries. `SunoAdapter.sidebarPlacement()` searches in order: (1) `afterend` of `a[href="/hooks"]`, (2) `beforebegin` of the profile split row (`.group\/profile-row` or `a[href^="/@"]`), (3) `beforeend` of the sidebar nav container. While the settings dialog is open, the button reflects `data-active=""` to highlight, reverting to `data-inactive=""` on close.
- **Disclosures (Lyrics, Style, Other Options) can be auto-collapsed upon activating the Advanced tab without interfering with manual user interaction.** When `closeDisclosuresOnAdvanced` is enabled (default `true`), `refreshMounts()` checks `isAdvancedTab()` and collapses expanded disclosures (`aria-expanded="true"`) on session entry. An `advancedSessionActive` and `autoCloseHandled` flag ensures this auto-collapse executes only once per tab activation session; subsequent manual user expansion is preserved across reactive re-renders and keystrokes until the user leaves and returns to the Advanced tab.
- **The Lyrics tag palette mounts with `afterend` beside `SunoAdapter.lyricsAnchor()` (`lyricsHeaderRow()`).** Palette buttons display clean labels without brackets (e.g. `Verse 1`), but insertion formats the tag with brackets (`[Verse 1]`) on an isolated line. Tag buttons prevent default on `mousedown` so caret selection inside the lyrics editor (Lexical `contenteditable` or `textarea`) is never lost on click. If the disclosure is collapsed when clicked, it automatically expands before insertion. Tags are editable in the settings dialog (`lyricsTagsSectionRef`, 1 tag per line).
- **The workspace clip list and the song detail panel both live on `/create` itself — no separate page/`matches` entry is needed to reach either.** Confirmed via a full-page dump of `/create` with the detail panel closed (`docs/showless.txt`) and expanded (`docs/showmore.txt`), on top of the existing `docs/alldom_ja.txt`/`alldom_en.txt`:
  - Each clip is `<div data-testid="clip-row" role="group" aria-label="<title>" data-clip-status="complete">`, containing exactly one `<a href="/song/<uuid>">` — this is the only place the extension can resolve a clip's title to its song id without touching a private API.
  - Its action-button row (いいね/Like, 低評価/Dislike, ワークスペースに固定/Pin, 共有/Share, then a 公開/Publish button) is where the "パラメータを再利用" / "Reuse parameters" control anchors (`SunoAdapter.clipRowActionAnchor()`, keyed off the いいね/Like button's `aria-label`), per the user's explicit choice over adding a Suno context-menu item - the menu is Base UI portal-rendered and was never captured in any DOM dump.
  - The row's own "その他のオプション" / "More options" context-menu trigger shares its aria-label with the disclosure heading `optionHeading()` looks for — see the `optionHeading()` bullet above.
  - The song detail right-pane panel shows `<div><span>Style Influence</span> <span>83%</span></div>` / `<div><span>Audio Influence</span> <span>70%</span></div>` **in English even on the Japanese UI**, and only for fields changed from their default (a sample with Weirdness untouched showed no Weirdness row at all). It does **not** show vocal gender, duration, Max Mode, personalization, mastering name, or preset name at all. This panel is intentionally **never read by the extension** - the take-history feature below records its own snapshot at generation time instead, both because of this panel's missing fields and because opening/parsing Suno's own portal-rendered panel is unconfirmed and brittle. Do not add a reader for it.
- **Take history records the full generation parameters at submission time and links them to Suno's own clip list by title, entirely independent of the song detail panel above.**
  - `SunoController.executeCreateWithTake()` calls a private `captureTakeSnapshot()` immediately before `triggerCreate()` on every Create submission (with or without a `{{TAKE}}` placeholder - see the next bullet), reading `adapter.readOtherOptions()`, `adapter.getStylePrompt()`, `adapter.getModelName()`, and the currently-selected style/mastering/preset from controller state. `readableOptionFields()` (`src/domain/logic.ts`) strips any field `readOtherOptions()` could not read, rather than storing the default value `emptyOtherOptions()` seeded it with as if it had genuinely been read - the same helper backs preset creation's "設定を保存" capture. The resulting `TakeRecord` is appended via `appendTakeRecord()` only if `triggerCreate()` reports success; a storage failure here is swallowed and must never fail the create flow itself (see the try/catch around it).
  - `SunoController.handleDocumentClick` now intercepts **every** Create button click, not only ones with a `{{TAKE}}` placeholder, so every submission gets a history record - the title-templating logic (steps 1/2/4/5 in `executeCreateWithTake()`) stays conditional on `usesTakePlaceholder`, only the recording and the `triggerCreate()` call itself are unconditional. The `isExecutingCreate` guard placed *inside* the `isCreateButton` branch (not before it) is load-bearing: it lets the synthetic click `triggerCreate()` dispatches pass through this same handler a second time *without* `preventDefault()`, which is what actually lets Suno's own click handler fire. Do not reorder these checks.
  - `SunoAdapter.getModelName()` reads the model selector button (`<button aria-expanded="…">v6</button>`, confirmed in `docs/showmore.txt`) - the only element on the create form starting with `v` + a digit under an `aria-expanded` selector, so no more specific selector was needed. Excludes `[data-testid="clip-row"]` and `suno-create-assistant` for the same reason `optionHeading()` does.
  - `src/suno/clip-linker.ts`'s `createClipLinker(adapter)` snapshots every song id visible via `adapter.clipRows()` at construction time (`seenAtStart`) so a pre-existing clip is never mistaken for a freshly generated one sharing its title. `linkPendingTakes()` matches unlinked records (`findUnlinkedTakeRecords()`) to clip rows that appeared *after* that snapshot, oldest record first; **every** currently-unclaimed title-matching row is attributed to one record (a single submission commonly yields more than one clip with the identical title). Two separate pending records that happen to share the exact same title are a known, accepted ambiguity: the older one claims all matching rows and the newer is left unlinked rather than guessed at - do not try to "fix" this by splitting rows between them without a stronger signal than title equality.
  - `entrypoints/suno.content.tsx`'s `syncClipButtons()` runs unconditionally on every `refreshMounts()` cycle (like the `settings`/`sidebar` mounts, not gated behind the `!advanced` return) because the clip list is visible regardless of which tab is selected. It is chained onto a `clipButtonSync` promise rather than fired in parallel, so two cycles inside the 80ms debounce window can't race each other's read-then-mount of the same `clip:<songId>` key. One `readStorage()` call builds a `songId → TakeRecord` map for all rows in a cycle, rather than one storage read per row.
  - The reuse-parameters button (`ReuseParamsButton` in `src/content/components.tsx`) mounts **in the Light DOM** (`shadow: false`) for the same reason as `SidebarSettingsButton`: it needs Suno's own `hxc-btn-*` classes to sit naturally among the row's other icon buttons, and a per-row Shadow DOM would duplicate the entire `suno-ui.css` stylesheet once per row. `SunoController.reuseTake()` calls `adapter.applyOtherOptions(record.options)` **only** - it deliberately never touches the Style field, leaving that to Suno's own "プロンプトを再利用" / "Reuse prompt" so the two don't fight over the same field.
  - A `clip:<songId>` key that trips the mounter's thrash detector (`onThrash`, see `mount.ts`) is added to `abandonedClipKeys` and never offered a fresh anchor/JSX again by `syncClipButtons()` - there is no fallback placement for a single row's own button the way `presetFallback` has one. This path is unverified against a real (possibly virtualized) clip list; if reuse buttons disappear or duplicate on a long/scrolled clip list, start here.

## Internationalization and multi-language architecture

- **Locale definitions live in `src/locales/`**:
  - `src/locales/types.ts`: Core types including `SupportedLanguage` (`'ja' | 'en'`), `SunoHostLocale` (host DOM selectors, headings, labels, regex patterns for Suno's native UI), `UiMessages` (extension UI strings and formatters), and `LocaleDefinition`.
  - `src/locales/ja.ts` & `src/locales/en.ts`: Language definitions for Japanese and English based on verified DOM dumps (`docs/alldom_ja.txt` and `docs/alldom_en.txt`).
  - `src/locales/index.ts`: Locale registry (`SUPPORTED_LOCALES`), language detection (`detectLanguage()`), getters (`getLocale()`, `getHostLocale()`, `getUiMessages()`), and cross-locale fallback query helpers (`getAllTitlePlaceholders()`, `getAllOptionResetLabels()`, `getAllSavedStyleTriggerLabels()`, `getAllSavedStyleMutationLabels()`, `getAllSavedStyleSaveNewLabels()`, `getAllClearFormLabels()`, `getAllClipRowLikeLabels()`, `getAllClipRowShareLabels()`, `getSliderLabels()`, `getRowLabels()`). `SunoController.handleDocumentClick` uses these (not hardcoded Japanese) to detect a saved-style mutation or Suno's own "Clear all form inputs" click regardless of UI language — don't reintroduce a language-specific string literal there.
- **Language detection**: `detectLanguage()` inspects `document.documentElement.lang` (e.g. `'ja'`, `'en-US'`) or `document.documentElement.dataset.language`, falling back to `'ja'`.
- **Hybrid fallback architecture for host DOM queries**: `SunoAdapter` queries using the detected host locale (`this.hostLocale`), but also leverages aggregated cross-locale patterns (e.g. searching all known title placeholders or reset labels) when inspecting inputs or headers. This guarantees that host controls can be found even during asynchronous language switches, hydration delays, or when Suno renders mixed-language strings.
- **Extension UI localization**: Content script components (`src/content/components.tsx`, `SettingsDialog.tsx`) and the controller (`src/suno/controller.ts`) retrieve localized copy via `getUiMessages(this.lang)`.
- **Confirmed English host DOM specifics (from `docs/alldom_en.txt`)**:
  - "その他のオプション" disclosure heading is **`More Options`** (not "Other Options"), and its reset action is `Reset All`.
  - Styles heading is `Styles` (with child `<div>Styles</div>` followed by prompt text); Lyrics heading is `Lyrics`.
  - Title input placeholder is `Song Title (Optional)`.
  - Excluded styles placeholder is `Exclude styles`.
  - Sliders `aria-label`: `Weirdness`, `Style Influence`, `Variety` (variation), `Audio Influence`.
  - Toggle button rows: `Vocal Gender` (`Male`, `Female`), `Duration` (`Custom`, `Auto`), `Max Mode` (`On`, `Off`), `Personalize` (`On`, `Off`, `My Taste`).
  - Saved Styles: trigger `aria-label="View saved style prompts"`, dialog `aria-label="Saved Styles"`, action buttons (`Delete`, `Rename`, `Grid View`) excluded from leaf prompt extraction. Suno's own "Save prompt" button (adds a new saved style directly from the style textarea) is `aria-label="Save prompt"`.
  - Suno's own "Clear all form inputs" action is `aria-label="Clear all form inputs"` (confirmed in `docs/alldom_en.txt`; do not assume a shorter "Clear all" or "Clear form").
  - Clip-row action buttons: `aria-label="Like clip"` / `"Share clip"` (used to anchor the reuse-parameters control planned for the workspace clip list).
- **Adding a new language**:
  1. Create `src/locales/<lang>.ts` implementing `LocaleDefinition` (`host` and `ui`).
  2. Add the language code to `SupportedLanguage` in `src/locales/types.ts`.
  3. Register the definition in `SUPPORTED_LOCALES` in `src/locales/index.ts`.
  4. Add unit test assertions in `tests/locales.test.ts`.

## Storage

`chrome.storage.local` holds schema version 2 (`CURRENT_SCHEMA_VERSION` in `src/domain/models.ts`): mastering prompts, option presets, the Auto title preference, the custom song title format (`titleFormat`), take numbers (`takeNumbers`), the disclosure auto-collapse preference (`closeDisclosuresOnAdvanced`), the custom lyrics tags list (`lyricsTags`), and the take history (`takeHistory`, capped by `takeHistoryLimit`, default `DEFAULT_TAKE_HISTORY_LIMIT` = 500). Tab-local selection state and saved-style caches must remain ephemeral.

- **`src/storage/repository.ts`'s `migrate()` upgrades an older stored value step by step (one entry per version in `migrations`, keyed by the version it upgrades *from*) and deliberately passes a *newer*-than-current value through unchanged rather than resetting it to defaults.** This matters because `readStorage()` used to treat anything but an exact `schemaVersion === 1` match as unreadable and silently reset the user's whole configuration — a real risk the moment a second schema version shipped. If you add a new schema version: add one migration step (old shape in, new shape + version out, never dropping a field), bump `CURRENT_SCHEMA_VERSION`, and do not touch the "future version passthrough" behavior in `migrate()`/`isKnownStorageShape()` — it is what protects a newer install's data from an older build of the extension (or a plain downgrade) reading it.
- **Export/Import (`SettingsDialog.tsx`'s "バックアップ" / "Backup" section) is a full-replace, not a merge.** `exportBackup()` returns the live `readStorage()` result (optionally with `takeHistory` zeroed out via its `includeTakeHistory` argument) as a downloadable JSON file; `parseBackup()` runs the same `migrate()` path so an export from an older build of the extension is upgraded on import rather than rejected or written back stale. There is intentionally no merge logic — resolving id/name collisions between the current and imported data was judged not worth the complexity for a personal-backup feature. All communication stays local (`Blob`/`URL.createObjectURL`, a `<input type="file">` read via `FileReader`/`File#text()`); nothing is ever sent anywhere.
